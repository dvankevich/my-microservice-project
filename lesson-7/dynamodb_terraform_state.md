# Чому таблиця DynamoDB більше не потрібна для Terraform State

## Контекст

Раніше для безпечного зберігання файлу стану (`terraform.tfstate`) в AWS S3 використовували зв'язку з двох сервісів:
- **Amazon S3** — для зберігання самого файлу стану;
- **Amazon DynamoDB** — для механізму блокування стану (*state locking*), щоб два процеси Terraform не змінювали інфраструктуру одночасно.

У нових версіях Terraform (починаючи з **1.10.0**) параметр `dynamodb_table` у блоці `backend "s3"` оголошено застарілим (`deprecated`), а натомість додано нативне блокування безпосередньо через S3.

## Як це працює зараз

У файлі `backend.tf` увімкнено параметр:

```hcl
terraform {
  backend "s3" {
    bucket       = "tfstate-bucket-lesson5"
    key          = "lesson-5/terraform.tfstate"
    region       = "eu-central-1"
    use_lockfile = true
    encrypt      = true
  }
}
```

Коли `use_lockfile = true`, під час виконання `terraform plan` або `terraform apply` Terraform автоматично створює тимчасовий файл блокування (`.tflock`) поруч із файлом стану в тому ж S3-бакеті та видаляє його після завершення операції.

## Переваги відмови від DynamoDB

1. **Менше інфраструктури:** не потрібно створювати, підтримувати та оплачувати окрему таблицю DynamoDB.
2. **Простіші права доступу (IAM):** достатньо налаштувати доступи лише для одного сервісу — S3, без додаткових політик для DynamoDB.
3. **Актуальний стандарт Terraform:** конфігурація не викликає попереджень `Warning: Deprecated Parameter` під час ініціалізації (`terraform init`).
4. **Повноцінний захист від конфліктів:** блокування при паралельних запусках продовжує працювати завдяки механізмам узгодженості та умовного запису S3.
